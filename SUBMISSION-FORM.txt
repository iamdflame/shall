FIELD 1 — PROJECT DESCRIPTION
================================================================================
----------------------------------------------------------------- copy from here

SHALL is a programming language whose source code is English requirements, and
a
compiler that refuses to build when those requirements do not say one thing.

A .shall program is a specification: a type signature plus acceptance criteria
in
EARS — the format Kiro generates. There is no implementation file. To compile
it,
SHALL sends the specification to an ensemble of independent language models,
each
given byte-identical instructions, none told the others exist. Every program
they
write is executed against the same generated inputs in an isolated sandbox, and
the results compared.

Agree, and the English determined the program, so SHALL emits it. Split, and it
did not — that is a compile error, reported the way a compiler reports one: the
responsible sentence, the phrase underlined, and the smallest input proving the
disagreement.

Consensus is not correctness, so a second pass turns each clause back into test
cases and runs the built program against them.

It answers a question nothing else answers: does this specification actually
say
one thing? Not "does a model think it is unclear" — that returns an opinion.
SHALL returns a measurement, with the input that proves it.

FIELD 2 — WHAT PROBLEM DOES THE PROJECT SOLVE?
================================================================================
----------------------------------------------------------------- copy from here

Spec-driven development assumes the specification means one thing. It often
means
two, and nobody finds out until production behaves in a way nobody specified.

Kiro, spec-kit and every requirements-based agentic workflow share that
unexamined
premise. Everything downstream inherits whatever the model happened to assume,
and
that assumption is invisible and unrecorded.

Measured, not hypothetical. Here is a complete specification:

    THE SYSTEM SHALL count the words in the text
    THE SYSTEM SHALL ignore words shorter than three letters

Six models — gpt-4o, gpt-4.1, o4-mini, gpt-5.2, gpt-5.6-luna, gpt-5.6-terra —
were each given it and asked to implement it. They returned THREE behaviourally
different programs:

    "well-known state-of-the-art"   four said 5, two said 2   (hyphens)
    "it's don't o'clock"            four said 2, two said 3   (apostrophes)
    "a1 22 333 4444"                five said 0, one said 2   (digits)
    "one,two;three"                 four said 3, two said 1   (punctuation)
    "ß Ünïcode naïve"               four said 1, two said 2   (accents)
        "..."                           five said 0, one said 1   (punctuation
    only)

Nobody wrote down what a "word" is. Each reader decided silently, and they did
not
decide alike. In a normal workflow one of those programs ships and the rest are
lost without trace.

Existing tools cannot catch this. Property-based testing needs the code to
exist.
Spec correctness checking assumes the spec means one thing — the assumption in
question. Formal methods answer it rigorously but charge you the English.
Asking a
model "is this ambiguous?" returns an opinion and cannot show you.

The cost is real: the bundled order-total example hides an ordering ambiguity
worth 6.48 on a single order — one reading returns 51.78, the other 58.26.

================================================================================
FIELD 3 — KEY FEATURES
================================================================================
----------------------------------------------------------------- copy from here

ENGLISH COMPILES TO A WORKING PROGRAM. One formal construct, the interface;
everything else is prose.

DISAGREEMENT IS A COMPILE ERROR, WITH THE SENTENCE NAMED. File and line, the
phrase underlined, why it is undefined, the input proving it, and which reader
returned what. Exit code 1, so it gates CI.

WITNESSES ARE MINIMISED. "well-known state-of-the-art" proves the readers
disagree; "a-a" proves it with nothing else in the input to blame.

BEHAVIOUR IS COMPARED, NEVER SOURCE. Two correct implementations often share no
lines. Each candidate's results across all probes form a behaviour vector.

A PLURALITY SETTLES NOTHING. Four against two is still an error — popularity is
precisely the question a specification exists to answer.

PROBES ARE SPEC-AWARE AND FREE. Deterministic, seeded from the specification's
own numeric literals, half the budget reserved for input interactions.

CONSENSUS IS CHECKED SEPARATELY FROM CORRECTNESS. Each clause becomes test
cases,
and the expectations are themselves filtered by reader agreement.

ORDERING AMBIGUITY IS ATTRIBUTED TO CLAUSE PAIRS — two precise sentences silent
about which applies first is the common case.

THE REPORT ENDS IN A DECISION. Each reading is offered as a rewrite; --apply
writes it and re-runs the check. The proposal is untrusted; the verification is
the deterministic oracle.

ARITHMETIC IS NOT AMBIGUITY. Float-only divergence is classified separately, so
an author is never sent to edit a sentence that was already correct.

UNTRUSTED CODE IS SANDBOXED. Fresh node:vm context, no host globals, wall-clock
timeout, and any candidate that carried state between probes is excluded by
name.

EVERYTHING REPLAYS FREE. Every example ships its recorded ensemble, so anyone
reproduces the exact results with no API key.

ANY VENDOR, NO NEW DEPENDENCY. Anthropic, Gemini, Groq, DeepSeek, Mistral,
OpenRouter, Together and Ollama all work through one compatible client.

THE REPO IS HELD TO ITS OWN KIRO SPEC. 50 criteria, each bound to code and to a
test. "npm run verify" reports 50 of 50.

REVIEWERS AND TECH LEADS — a specification gains a machine-checkable property:

approving a spec today has nothing but their own reading to go on.

PRODUCT MANAGERS AND BAs WRITING ACCEPTANCE CRITERIA — "shall lint" needs no
API
key and no engineering knowledge. It names open wording (word, sort, between,
average) and says why each is undefined.

TEAMS IN REGULATED OR HIGH-CONSEQUENCE DOMAINS — ambiguity in billing, pricing
or
eligibility is an incident waiting to happen. The bundled example is a 6.48
discrepancy hidden in one ordinary sentence.

RESEARCHERS ON MODEL AGREEMENT — a reproducible harness for measuring
inter-model
behavioural agreement, with recordings committed so anyone can re-run the
results
for free.

FIELD 9 — SETUP AND TESTING NOTES
================================================================================
----------------------------------------------------------------- copy from here

NO API KEY NEEDED. Every example ships its recorded ensemble, committed to the
repository, so all evaluation runs offline and free. Verified from a clean
clone
with the key variables explicitly unset.

Requirements: Node.js 20 or newer. Nothing else — no database, no Docker, no
environment variables.

    git clone https://github.com/iamdflame/shall && cd shall
    npm install && npm run build
    npm run install-cli

Use "npm run install-cli", NOT "npm link" — npm's global prefix is a system
directory on most Linux installs and npm link fails with a permissions error.
Every "shall ..." command also works as "node dist/shall/cli.js ...".

THE ONE COMMAND THAT SHOWS EVERYTHING

    shall check examples/word-count.shall

Expect: AMBIGUOUS SPECIFICATION, the clause at line 10 with "words" underlined,
minimal witness text = "a-a", and the six readers grouped by what each
returned.
Exit code 1, about 2 seconds.

THEN ONE SENTENCE FIXES IT

    shall check examples/word-count.fixed.shall

Expect: UNAMBIGUOUS, six readers agreeing on all 33 probes, CONFORMANCE 100%.
Exit code 0.

ALSO

        npm run findings    12 checks, ~15s, reproduces all four documented
    findings
    npm run verify      the repo against its own Kiro spec — 50 of 50
    npm test            148 tests
    shall lint <file>   static scan, no model, no key

Only "--live" and "shall suggest" need a key. Nothing in the evaluation path
does.
CI runs the tests, all four findings and the self-verification with no secrets.

NOTE ON COMMIT HISTORY: the first commit contains the whole initial project;
everything after it is incremental. PROVENANCE.md states this plainly and lists
the evidence that does exist. Raised here rather than left to be noticed.

Known limitations are in the README. The sharpest: readers are currently all
one
vendor, and the cross-vendor delta is not yet measured.

FIELD 11 — BRIEFLY EXPLAIN HOW KIRO WAS USED
================================================================================
----------------------------------------------------------------- copy from here

Kiro is the substrate this project operates on. .kiro/ is SHALL's runtime
input,
not build residue left over from generating code once.

SPEC-DRIVEN THROUGHOUT — four spec folders, 50 EARS acceptance criteria.
shall-language (25, with design.md recording the reasoning behind each
architectural decision and tasks.md tracing 49 tasks), plus offline-replay (9),
disambiguation (10) and multi-vendor-ensemble (6). Each subsystem was specified
before it was built.

STEERING SHAPED THE CODE — three documents loaded into every interaction.
tech.md encodes the one-runtime-dependency rule and the provider boundary;
structure.md encodes the layering rule. Both are visible in the result: exactly
one dependency, and no vendor SDK imported outside provider/.

HOOKS CLOSE THE LOOP — three agent hooks: re-verify on any source save; lint
any
.shall file on save (free, no key); and prompt for re-verification when a
requirements document changes, because editing a criterion voids its proof.

ENFORCED, NOT DECORATIVE — every criterion carries a @shall annotation on the
code implementing it and the test proving it. "npm run verify" joins each test
result back to the criterion it proves and reports 50 of 50. Judges can run it.

THE PRODUCT CONSUMES KIRO'S FORMAT — a .shall program is written in the same
EARS
syntax Kiro generates. SHALL answers a question Kiro's workflow raises but
cannot
answer: whether the requirements actually say one thing.

Writing the three newer specs found two real defects: adding a second spec made
every bare "@shall 1.1" ambiguous across specs — the tool's own guard firing on
its own repository — and the binding scanner bound only the last of several
stacked annotations. Both fixed and covered by tests. Specs were not paperwork.

FIELD 13 — THIRD-PARTY APIs, DATASETS, LIBRARIES OR ASSETS
================================================================================
----------------------------------------------------------------- copy from here

LIBRARIES — exactly one. A production install brings in openai 7.5.0
(Apache-2.0) and nothing else; TypeScript and @types/node are dev-only.
Everything else is the Node standard library — node:vm for the sandbox,
node:crypto for cache keys, node:child_process for the test runner. No
framework,
bundler, test framework or assertion library. The site is plain HTML/CSS/JS.

APIs — OpenAI, for the ensemble compiler, probe generation, expectation
derivation and "shall suggest". Default roster: gpt-4o, gpt-4.1, o4-mini,
gpt-5.2, gpt-5.6-luna, gpt-5.6-terra. Judges do not need it — every example
ships
its recorded ensemble, so evaluation runs offline. Anthropic, Gemini, Groq,
DeepSeek, Mistral, OpenRouter, Together and Ollama are also supported, but none
is contacted unless its environment variable is set.

DATASETS — none. No training data, no downloaded corpus. The seven example
specifications were written for this project, and probe inputs are computed at
runtime from the type signature and the spec's own numeric literals.
recordings/
holds 47 verbatim outputs from our own API calls, committed so anyone can
replay
them — a record of this project's runs, not a third-party dataset.

FONTS — Spectral and IBM Plex Mono/Sans via Google Fonts, both SIL Open Font
License.

ASSETS — all original. Logo, wordmark, end card and thumbnail were designed for
this project, and each PNG regenerates from an HTML file committed beside it.
No
stock images, icons or templates.

USED TO PRODUCE THE SUBMISSION, not part of the product: ElevenLabs (video
narration), Vercel (site hosting), YouTube (video), Kiro (the IDE it was built
with).

FIELD 14 — PAID SERVICES, RATE LIMITS, OR SETUP REQUIREMENTS
================================================================================
----------------------------------------------------------------- copy from here

NOTHING IN THE EVALUATION PATH COSTS MONEY OR NEEDS AN ACCOUNT. No API key, no
credentials, no payment. Verified from a clean clone with OPENAI_API_KEY,
ANTHROPIC_API_KEY and GEMINI_API_KEY explicitly unset: the full ambiguity
report,
all 12 findings checks, and 50/50 on verify all still run.

SETUP — Node.js 20 or newer, and nothing else. No database, no Docker, no
services, no environment variables, no config file. Three commands, one
package,
installs in seconds. Use "npm run install-cli", not "npm link" (npm's global
prefix is a system directory on most Linux installs and npm link fails).

PAID — only if you choose to run live. A key is needed for "--live" and "shall
suggest" only. One example live costs roughly 0.02 to 0.05 USD: six model calls
plus one for probe generation. "shall check <file> --dry-run" reports the
estimate
and which readers are reachable before anything is spent. Any OpenAI-compatible
vendor works instead.

RATE LIMITS — none apply to evaluation, which makes no network calls. Running
live calls six readers concurrently, which on a new low-tier account can hit a
per-minute limit. A rate-limited reader is named and dropped rather than
crashing
the run, and if fewer survive than the quorum the build is refused rather than
reporting a false consensus over too few readers.

ALREADY PAID BY US — the 47 committed recordings were produced with our own
credits. That expense is exactly what makes evaluation free for everyone else.
